# LDA Local Graph

Part of **Local Developer Accelerator for Optimizely** — by Coding Koala. Compatible with Optimizely Graph for CMS 13.

## Install with the LDA CLI

```powershell
irm https://github.com/coding-koala-io/local-developer-accelerator/releases/latest/download/install.ps1 | iex
lda install graph
```

`lda self-update` updates the CLI.

A single Node.js process that accepts content and type pushes from an Optimizely CMS 13 site and answers its GraphQL queries locally.

## Why this exists

- **Faster inner loop.** Build and debug CMS 13 sites that use Graph without waiting on a cloud service: publish, sync and query all happen on your machine.
- **Works offline.** Develop and debug against the Graph APIs on your own machine, with no wait for a cloud sync.
- **Everything is visible.** Every sync and query request is recorded in a request log, with raw documents, sync journals and jobs, so integration problems can be traced to the exact request.
- **Several sites, one instance.** Multiple CMS sites can run against one local server, each with its own isolated data and keys.
- **Easy to reset and replay.** Clear content, types, history or everything for one site and run a full synchronization again in seconds.

It is for development and research use only.

## Getting started from source

1. **Requirements:** Node.js 24 or later, and a CMS 13 site (with the Optimizely Graph packages) that you can run locally.
2. **Install and start:**

   ```powershell
   git clone https://github.com/coding-koala-io/lda-graph.git
   cd lda-graph
   npm install
   npm start
   ```

   The server listens on <http://localhost:8082>.
3. **Create an instance.** Open <http://localhost:8082/>, type a name in **New tenant** and click **Create tenant**. The page then shows the generated `Optimizely:ContentGraph` settings; copy them. They look like this (your keys and secret will differ):

   ```json
   {
     "Optimizely": {
       "ContentGraph": {
         "GatewayAddress": "http://localhost:8082",
         "AppKey": "app-my-site-0123abcd",
         "Secret": "<generated Base64 secret>",
         "SingleKey": "pub-my-site-4567ef89"
       }
     }
   }
   ```

4. **Connect the CMS.** Paste the settings into the CMS site's `appsettings.Development.json` and start the CMS. Start this server first: the CMS refuses to start when the Graph address is unreachable.
5. **Synchronize.** In the CMS admin UI, open **Scheduled Jobs** and run **Optimizely Graph Full Synchronization**. The dashboard counts update when it finishes.
6. **Use it:**
   - **Explorer** (`/explorer`): browse content types, items and full-text search results, and open any item in GraphiQL.
   - **GraphiQL** (`/graphiql`): run queries. The CMS **Settings → GraphiQL** page also works against this server.
   - **Request log**: each tenant page lists the last 200 requests with full request and response details.
   - **Clear / reset**: the tenant page's Danger zone clears content, types, sync history, the request log, or everything.
   - **Smooth rebuild**: the CMS smooth rebuild feature works locally (see [Smooth rebuild](#smooth-rebuild)).

Optional: run it as a Windows service so it starts with your machine (see [Run as a Windows service](#run-as-a-windows-service)).

## Troubleshooting

- **The CMS will not start.** This server is not running, or `GatewayAddress` points to the wrong host or port. Start the server first and check the address.
- **"Secret must be Base64".** The CMS preview service requires a Base64 secret. Use the secret generated by the dashboard.
- **Nothing shows up after publishing.** Open the tenant's request log to see whether the CMS sent anything, then run **Optimizely Graph Full Synchronization** again.
- **Port 8082 is already in use.** Start on another port with the `PORT` environment variable (for example `$env:PORT = '8090'; npm start`) and update `GatewayAddress`.
- **After `git pull`.** Run `npm install`, then restart the server. With the Windows service: stop the service first, then pull and install, then start it again.
- **Updating an older CLI installation.** Earlier documentation used `npm i -g https://github.com/coding-koala-io/local-developer-accelerator/releases/download/v1.0.0/coding-koala-io-accelerator-1.0.0.tgz`. Use the installer above for new installations and `lda self-update` for existing ones. Once the CLI is published to npm, `npm i -g @coding-koala-io/accelerator` will also be available.

### Authentication and visibility

The three auth kinds are single, basic, and preview. Push APIs and slot mutations require Basic authentication. Single-key queries show only published, unexpired, undeleted documents readable by Everyone. Basic queries include drafts and expired documents; `cg-roles` and `cg-username` constrain ACLs, `cg-include-deleted: true` includes soft deletions, and `cg-include-expired: false` hides expired content. Role/user values are URI-decoded.

Preview queries accept `Authorization: Bearer <jwt>`. HS256 signatures use the Base64-decoded secret; issuer/audience must be `graph`, and a configured app key must match. JWT `sub`/`role` claims supply username/roles and override request ACL headers. An empty server secret skips signature verification. Expired JWTs are accepted and logged, matching the CMS behaviour; the token's roles still constrain content access. Basic continues to use the raw secret text as its password.

Preview tokens can read drafts through the user's ACLs but cannot execute slot mutations or call push/admin endpoints. Missing or malformed `_rbac` is visible only to Basic without ACL headers. ContentReference `item` and other model `ref` properties resolve documents by `_id` in the selected slot, with the same auth, ACL, status, deletion, and expiry rules as root queries. Missing or inaccessible references return null; content objects and their fallbacks implement `IData`, allowing fragments on concrete types or `_IContent`.

### CORS and browser access

CORS is available only for GraphQL API `GET`, `POST` and `OPTIONS` on `/content/v2`. Allowed-origin `OPTIONS` preflights return 204 before authentication. Set `CORS_ORIGINS` to a comma-separated allowlist; the default `*` reflects any origin. Same-origin requests remain accepted. Allowed responses include `Access-Control-Allow-Origin` reflecting the request Origin (or `*` when absent), `Vary: Origin`, allowed methods `GET, POST, OPTIONS`, and a 600-second max age. Allowed headers are `Authorization`, `Content-Type`, `X-Query-Name`, `cg-username`, `cg-roles`, `cg-include-deleted`, `cg-include-expired`, `cg-use-new`, `cg-query-new`, and `cg-deploy-new`. GraphiQL, the explorer, the tenant picker, dashboard pages and GET queries have no CORS headers and reject cross-origin requests with 403.

On `/content/v2`, cross-origin requests carrying Basic credentials return 403; cross-origin mutations also return 403, including requests with single or preview credentials. Browser queries can use single keys or preview Bearer tokens. Push/admin routes, `/__debug/*`, and `/` have no CORS headers: cross-origin requests and all `OPTIONS` return 403. Requests without Origin remain available to server-side clients. Same-origin means `http://127.0.0.1:<actual-port>`, `http://localhost:<actual-port>`, or `http://<HOST>:<actual-port>`. On non-loopback binds, valid ADMIN Basic credentials also allow an Origin exactly matching `http(s)://<request Host>`. `PUBLIC_HOSTNAMES` adds explicitly trusted hosts/origins. On loopback bindings, unexpected Host names or ports return 403 to prevent DNS rebinding; non-loopback bindings accept other Host names.

### Query behaviour

Queries accept the CMS's JSON-string variables, locale enums, variations, nested filters, scoring, ordering, cursors, facets, autocomplete, and metadata/content interfaces. String equality (`eq`, `notEq`, `in`, `notIn`) is case-insensitive. Missing required model properties remain nullable. Malformed GraphQL returns errors with HTTP 200; successful responses omit `errors` entirely and include a correlation ID.

Model-aware output coercion keeps malformed stored field values from creating GraphQL `errors`. Int and Float accept numeric strings; invalid or non-finite values become null (Int also requires a signed 32-bit integer). Boolean accepts booleans and the strings `"true"`/`"false"`, otherwise null. String values are converted to text, with objects JSON-stringified. List fields wrap a scalar in an array and drop elements that cannot be coerced; explicit null elements remain null. Object/interface fields given a non-object become null. Nested fields follow the same rules, and one warning is logged per document and field when coercion repairs or rejects a value. Raw documents remain available unchanged for debugging.

String fields and `_fulltext` support `phrase`, `wildcard`, and string-valued `fuzzy`. Phrase matches consecutive Unicode tokens; wildcard applies case-insensitive `*`/`?` globs to tokens. Fuzzy uses Damerau-Levenshtein distance, including adjacent transpositions: distance at most 1, or at most 2 for query tokens longer than 5 characters. Matching clauses contribute relevance multiplied by `boost`. Synonyms remain accepted and ignored. JSON output parses stored JSON strings, including RichText `json`, while ordinary non-JSON strings remain strings.

Facet `filters` also narrow `items`, `item`, `total`, paging, and autocomplete: a document must match at least one supplied value for each filtered field. Counts for a facet are computed before applying its own filter, while applying filters from other fields, so other choices remain available. For example, `facets { Tags(filters:["News"]) { name count } }` restricts results to News documents but still reports other tags' counts. Variables, fragments, aliases, and selection directives are respected.

With numeric `ranges`, filter values are range names such as `"0-10"`: membership is lower-inclusive and upper-exclusive. Omitted bounds use `*`, for example `"*-0"` and `"20-*"`. A list-valued field matches when any element belongs to a selected range; each document contributes at most one count per range.

Documents retain raw payloads alongside recursively normalized keys. `$$Type`, `___searchable`, and `___skip` suffixes disappear from query field names; skipped data remains readable but cannot match filters or fulltext.

## Tenants and routing

The dashboard's **New tenant** form writes `tenants.json` for you. You can also create it by hand in the working directory, or set `TENANTS_FILE` to another path:

```json
{
  "tenants": [
    { "id": "site-a", "name": "Site A", "appKey": "site-a", "secret": "MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=", "singleKey": "site-a-public" },
    { "id": "site-b", "name": "Site B", "appKey": "site-b", "secret": "YWJjZGVmMDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODk=", "singleKey": "site-b-public" }
  ]
}
```

IDs must match `^[a-z0-9][a-z0-9-]{0,62}$` and be unique. AppKey and SingleKey must match `^[A-Za-z0-9._~-]{1,200}$` and be unique across both key sets; a public key cannot equal any app key. Secret must be nonempty without leading/trailing whitespace. Invalid config prevents startup with the entry number/ID; invalid Base64 produces a warning because CMS preview needs Base64. The file overrides all `GRAPH_*` credential settings, with a warning if they are also set.

Basic `base64(appKey:secret)` selects an account by app key and verifies its raw secret with constant-time comparison. `Authorization: epi-single <key>` or `/content/v2?auth=<key>` selects by SingleKey. Bearer preview JWTs select by their `appKey` claim, then verify HS256 using that tenant's Base64-decoded secret and `graph` issuer/audience. A token signed with A's secret while claiming B's app key fails. Missing/unknown credentials return 401 `{"message":"Unknown or missing credentials"}`. Basic, single and preview visibility/mutation rules stay the same inside each account. Tenant A cannot read tenant B's journal/job even when its ID is known.

Without a file, the `default` tenant keeps the original `GRAPH_*` rules, including permissive empty keys and paired Basic settings. Hot reload watches file changes with a 300 ms debounce: valid additions, removals, name changes and key rotations apply without restarting. Invalid edits keep the previous configuration and log the error. Removing a tenant flushes and evicts its runtime, retaining its folders. Changing an ID through the dashboard moves both data and log folders after flushing pending writes, evicting the old runtime. A file edit is recognized as a rename when the old ID disappears and the appKey stays the same. Existing destination folders cause rejection; they are never overwritten.

Stores and schemas load on first use and stay in memory. `GET /health` always returns `status: "ok"`, `product` (`graph`), `version` and `dataVersion`, to every caller. Loopback callers, and callers with valid ADMIN Basic credentials on non-loopback binds, also receive `tenants: { "site-a": { "loaded": false, "docs": 0 }, ... }` and process memory, without loading stores.

`tenants.json` records `"dataVersion": 1` (a file without it is read as version 1). The server refuses to start, with exit code 3 and without changing the file, when the file was written by a newer version (`Data in <path> was written by a newer version (dataVersion <n>). Upgrade LDA Local Graph or restore a backup.`) or when `dataVersion` is not a positive whole number (`Data in <path> has an invalid dataVersion (<value>).`). Upgrade, restore a backup or correct the value, then start again. Tenant dashboards and selected-tenant explorers count as use. The main dashboard and explorer picker show "not loaded" without loading stores; choose Load or open a tenant to load it. First loads log store size and elapsed time. Admin health also includes recycle status (enabled, thresholdMb and last). Every account has its own types, live/new slots, docs, tombstones, journals, jobs, webhooks, and request history. Disk paths are `DATA_DIR/<tenantId>/store.ndjson` and `LOG_DIR/<tenantId>/requests.ndjson`; failed routing goes to `LOG_DIR/_unrouted/requests.ndjson`. Logs rotate independently at 50 MB. Console lines start with `[site-a]`, including GraphQL root/query name and stream ops/journal details. Bodies are bounded to 64 KB and marked when truncated; Authorization is reduced to its scheme and every logged URL redacts `?auth=` values as `auth=***`.

If a root-level `DATA_DIR/store.ndjson` or `store.json` exists and `default` has no folder, it moves into `DATA_DIR/default/`, including migration/quarantine markers. Root-level `LOG_DIR/requests.ndjson*` files also move into `LOG_DIR/default/`, including rotated logs. Existing stores/log files are never overwritten; conflicting root logs remain in place with a warning. Without a default account, the root store stays in place with an import warning. Choose **Import legacy store** on an empty tenant page to move it into that account. Nonempty destinations are rejected; a destination's empty persisted files are archived under `before-import-<id>/` so they cannot hide an imported legacy JSON file. Existing NDJSON/JSON compatibility, corruption quarantine, migration markers and shutdown saves apply inside each tenant directory.

## Dashboard and debugging

Every page shows a development-only banner and a footer with links to **About** (`/about`: product, version, data version, publisher and licence), **Privacy**, **Licence** and **Legal notice** (`/about/privacy`, `/about/licence`, `/about/legal`), which display PRIVACY.md, LICENSE.md and LEGAL-NOTICE.md from the installation folder. About pages follow the same access rules as the dashboard. In GraphiQL, which the CMS can show inside its own window, the header and footer links open in a new tab.

`GET /` lists tenant names/IDs, keys (AppKey and SingleKey are click-to-reveal), Published/Draft/other document counts, content types, languages, last full sync, last request and disk size, with links to GraphiQL and the explorer. Open a tenant at `/tenants/{id}` for its exact appsettings snippet, overview, last 50 sync jobs with indexed/deleted/failed counts and journal items, searchable documents (50 per page), versions of a key, last 200 requests and full request/response details, and searchable SDL. Overview counts refresh every five seconds. Content and all user values are HTML-escaped.

The New tenant form asks only for a required name (1–100 characters after trimming). The server generates a lowercase slug ID (up to 40 characters, falling back to `instance`, with `-2`, `-3`, … for collisions), unique `app-<id>-<8 random hex>` and `pub-<id>-<8 random hex>` keys, and a standard Base64 secret from 32 random bytes. Creation redirects to the highlighted Connect section with a flash prompting you to copy the generated settings into the CMS `appsettings.Development.json`; GatewayAddress uses the request host. The edit page retains name, ID, keys, secret and Generate secret controls. Forms validate inline and atomically write `tenants.json`; the resolved `TENANTS_FILE` path is shown on the dashboard.

The first dashboard write preserves all explicit env credentials for `default`. If any env key is empty, writes are blocked by **Give the default instance explicit keys first**, prefilled with generated missing keys. Only saving that form creates the file; update the running CMS appsettings to match the displayed keys. Before every dashboard write, the file is re-read: any change since the last successful load/save blocks the write with “tenants.json was changed on disk — reload or fix it first”, including parse errors for invalid edits.

### Administration access

Loopback dashboard/debug administration needs no credentials and still enforces the configured same-origin/Host checks. Non-loopback dashboard, explorer and GraphiQL access require independent admin Basic; startup refuses to run without both `ADMIN_USER` and `ADMIN_PASSWORD`. Protected pages respond with `WWW-Authenticate: Basic realm="LDA Local Graph"`; CMS tenant keys are not admin credentials, and admin credentials do not route CMS queries.

Remote browser administration works through a network name even with `HOST=0.0.0.0`: an Origin matching the request Host is accepted only with valid ADMIN Basic credentials. Both HTTP and HTTPS origins are supported for a reverse proxy. Configure `PUBLIC_HOSTNAMES` for additional trusted hostnames/origins; loopback binds retain their Host checks with these explicit additions. These settings exist for unusual local setups such as a VM or container on your own machine; they do not make this tool suitable for shared use.

### Clearing data

All dashboard POST forms require a per-process CSRF token, so a form opened before restart must be reloaded. Destructive forms first show a confirmation page and require typing the exact tenant ID. Clear content removes docs/tombstones in live, new and previous slots, deletes the previous slot, and keeps live/new types (run CMS Full Synchronization again); Clear content types removes models and resets schemas, reporting separate content-type and property-type counts across all models in all slots; Clear sync history removes journals/jobs; Clear request log removes memory and rotated files; Reset everything also removes webhooks, the new slot and the previous slot. Delete tenant optionally deletes its data/log folders. Redirects show exact removal counts. Clear-log actions are recorded in `_unrouted` so they leave the tenant log empty.

JSON equivalents are available for local tooling, using `Content-Type: application/json`:

```http
POST /tenants/{id}/clear

{"what":["content","jobs"]}
```

The response is `{"removed":{"docs":3,"tombstones":2,"jobs":1,"journals":1}}` with actual counts. Accepted values are `content`, `types`, `jobs`, `requests`, and `all`. JSON callers use independent admin Basic on non-loopback; browser Origin/Host rules still apply. Typed confirmation and CSRF are required for HTML form submissions, while this JSON API supports programmatic clear operations.

## Two CMS sites on one server

1. Create one tenant per site on the dashboard (or save the two-account `tenants.json` above). Start the server once with `npm start`.
2. Open <http://localhost:8082/tenants/site-a>. Copy its Connect snippet into site A's `appsettings.Development.json`.
3. Open <http://localhost:8082/tenants/site-b>. Copy its snippet into site B. Both use the same GatewayAddress but different AppKey, Secret and SingleKey.
4. Start both CMS sites and run **Optimizely Graph Full Synchronization** in each. Open each tenant's Sync jobs section to inspect its result.
5. Query `/graphiql?tenant=site-a` and `/graphiql?tenant=site-b`. Publishing or clearing one account does not change the other, even if both CMS databases use identical document IDs.

## Media text extraction

`POST /extract` extracts plain text, PDF and Word `.docx` media and returns plain text for indexing and fulltext search. Old `.doc`, PowerPoint, Excel and scanned (image-only) PDFs return no text. Files above the CMS limit (5 MB by default) are never sent by the CMS. Extraction detects the format from the bytes, loads parsers lazily, and returns empty text on failure or timeout.

## Smooth rebuild

`deployNewAccountVersion` creates a fresh empty new slot while keeping any previous slot. Push types/documents there with `cg-deploy-new: true` or index documents with `version: "new"`. Query it with `cg-query-new: true` (case-insensitive value); `cg-use-new: true` remains supported. Without either header, queries use live. `/graphiql?tenant={id}&slot=new` selects new, and the visible **Query: live / new slot** toggle switches the query header.

`useNewAccountVersion` accepts the new slot and saves the former live types, documents, tombstones and type-update metadata as the previous slot, replacing an earlier snapshot. CMS **Settings → Smooth Rebuild** can then offer **Revert to the state at …**: `useOldAccountVersion` restores that previous live state and removes both previous and pending slots. Without a previous slot, it just drops pending. `abandonSlot` drops pending and keeps the previous state available for revert. Previous slots persist across restarts, appear as `slots.old` in tenant stats and as **previous (revertable): N docs** on the dashboard, and have no query schema. Content reset/purge also deletes the previous slot. By default the previous slot expires 24 hours after promotion (PREVIOUS_SLOT_HOURS=24). The persisted oldSlotSince timestamp survives restarts; expiry is checked on load and every 10 minutes. The tenant dashboard shows the expiry time. Set PREVIOUS_SLOT_HOURS=0 to keep it forever. Older stores without a timestamp start their retention period on first load.

The CMS **Settings → GraphiQL** page works through its iframe URL `/app/graphiql?auth=<SingleKey>`. It selects the tenant by SingleKey, queries same-origin `/content/v2` with `Authorization: epi-single <key>`, and provides the same live/new toggle (including `?slot=new`). No framing headers are added, and request URLs keep redacting `auth=***`.

### Deletes and persistence

Timestamped deletes retain a tombstone per `_id` in each slot, including matches from `delete_by_paths`. Older deletes are ignored when a newer document or tombstone exists; an index older than a tombstone is a journal `noop`, preventing late batches from restoring deleted content. Tombstones persist and follow slot promotion; newer indexes can restore content.

Persistence coalesces changes for 500 ms without postponing an already scheduled save, so continuous pushes cannot exceed the 10-second maximum start delay unless a snapshot is already in flight. It uses asynchronous filesystem writes with one in-flight save and coalesced follow-up saves. Each save copies the slot maps at its start, retains immutable document records, clones mutable metadata/type data, and always promotes that consistent revision before saving newer changes. Shutdown skips a snapshot when the last completed revision is still current; explicit embedding calls to flush() continue to force a snapshot. `store.ndjson` contains one record per raw document, type model, tombstone, journal, job, webhook, or pending-slot marker; normalized documents/search paths are rebuilt on load. Writes use bounded batches, a temporary file, and atomic rename, then flush on server close/SIGINT/SIGTERM/SIGBREAK. Legacy `store.json` is read only before migration: after the first successful NDJSON write it is renamed to `store.json.migrated-<timestamp>-<id>`. A failed write leaves the legacy source intact. An existing NDJSON store, a migration marker, or a quarantined NDJSON store prevents legacy fallback, so stale data cannot reappear after corruption or file removal. Corrupt or partial stores are quarantined as `store.corrupt-<timestamp>-<id>.json` (or `.ndjson`), a clear warning is logged, and startup continues empty. Shutdown save failures are caught and logged. The store retains the last 1,000 journals and 200 jobs.

## Run as a Windows service

The Windows service is a convenience for your own development machine: it keeps the local server running in the background so you do not have to start it by hand. It is not a server deployment and does not change the development-only scope above.

With Node.js 24 and dependencies installed (`npm install`), run this from the repository:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 install
```

Install opens a Windows UAC prompt when administrator access is needed. It downloads **WinSW v2.12.0 x64**, verifies SHA-256 `05B82D46AD331CC16BDC00DE5C6332C1EF818DF8CEEFCD49C726553209B3A0DA`, and verifies the same pinned hash before reusing an existing wrapper. A mismatch aborts before service changes. The service runs as `NT AUTHORITY\LocalService`, starts automatically with a delayed start, restarts after crashes, and allows 15 seconds for shutdown saves (Ctrl+C/SIGINT/SIGTERM/SIGBREAK). Runtime permissions remove inheritance and grant SYSTEM and Administrators Full control, and LocalService Modify. LocalService and local Users have Read/Execute on the service directory (wrapper/XML/console logs, no secrets, so status/logs/plan work without admin), LocalService has Read/Execute on the repository, with Modify restored only on `service\logs` and the single `service\LdaGraph.wrapper.log` file. Before install, uninstall, start, stop or restart changes anything, the script checks every folder from below the drive root down to the runtime folder and its `service` folder: none may be a junction or symbolic link; each must be owned by SYSTEM, Administrators, TrustedInstaller or the current elevated user (ProgramData and Program Files themselves by SYSTEM, Administrators or TrustedInstaller); and no account other than SYSTEM, Administrators, TrustedInstaller or CREATOR OWNER (inherit-only) may write, delete, change permissions or take ownership. LocalService may write only to the runtime folder, `data`, `logs` and `service\logs`. The command refuses otherwise and names the folder and the account (for example a folder on a second drive that Authenticated Users can modify, which is the Windows default for new top-level folders there). Missing folders are created with restricted permissions from the start (SYSTEM and Administrators Full control; Users and LocalService Read/Execute on created parent folders), and `service`, `data`, `logs` and `service\logs` are checked again right before use. Node.js must be installed system-wide (for example `C:\Program Files\nodejs`): install refuses a `node.exe` whose folder other accounts can change, such as an nvm or AppData install. `icacls.exe`, `sc.exe` and the UAC `powershell.exe` always run from the Windows system folder. Keep Node and the repository accessible at their installed absolute paths.

Install replaces the runtime and service directory DACLs completely, removing unrelated explicit grants as well as inherited permissions, before generating or importing credentials and data. Child permissions are reset before those writes and again after installation files are written.

After install, run `icacls "C:\ProgramData\Coding Koala\Local Developer Accelerator\Graph\tenants.json"` as a manual check: it must show no `BUILTIN\Users` entry. Check that LocalService has only Read/Execute on the wrapper and XML, and Modify on the log paths. WinSW 2.12 logging uses the configured `logpath` for its wrapper log; the single beside-executable log remains writable for existing runtimes without granting Modify on the service directory.

Files live outside the repository at `C:\ProgramData\Coding Koala\Local Developer Accelerator\Graph`:

| Path | Contents |
| --- | --- |
| `tenants.json` | Tenant configuration/credentials, generated once and preserved on reinstall. |
| `data\` | Per-tenant stores. |
| `logs\` | Per-tenant request logs. |
| `service\` | Downloaded `LdaGraph.exe`, generated XML and wrapper diagnostics. |
| `service\logs\` | Server stdout/stderr and wrapper logs; 10 MB rotation, five archives. |

A fresh install creates one tenant named **Default** using the dashboard's generation rules and prints its CMS appsettings snippet. Open `http://localhost:8082/`, open the tenant, and copy **Connect** into the CMS site's `appsettings.Development.json`. Start the CMS and run **Optimizely Graph Full Synchronization**. Developer mode (`npm start`) keeps its existing local/environment paths.

To copy an existing developer runtime on first install, or choose another port/runtime root:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 install -Port 9082 -RuntimeRoot D:\GraphRuntime -ImportFrom D:\PreviousGraphRuntime
```

`-ImportFrom` copies `tenants.json`, `data` and `logs` only when the destination `tenants.json` is absent; if it already exists, install fails before making changes and explicitly reports that the import was not applied. Existing destination data/log content is rejected rather than overwritten. Reinstall preserves existing runtime files and keeps the existing configured port unless `-Port` is given. Later commands without `-RuntimeRoot` use the folder of the installed service, so `npm run service:*` keeps working after a move to another folder or drive; start/restart/status read the port from its XML.

`-MaxMemoryMB` sets Node's old-space heap budget (default **8192 MB**, valid range **1024–65536**). For example:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 install -MaxMemoryMB 16384
```

Call the script directly as shown: `npm run service:install -- -MaxMemoryMB 16384` does not work from PowerShell, because PowerShell drops the `--` and npm then treats `-MaxMemoryMB` as its own option. The generated Node arguments place `--max-old-space-size=<MaxMemoryMB>` before the server script. Reinstall keeps the value in the existing service XML unless `-MaxMemoryMB` is passed; older XML without the flag uses the default. `plan` prints the selected value and whether it is the default, explicit, or kept from existing config. This heap budget is not a cap on total process RSS.

Out-of-memory symptom: **service stops after repeated restarts; err log shows JavaScript heap out of memory**. Inspect `service:logs`, process memory on the dashboard or admin `/health`, and loaded document counts per tenant. The dashboard warns above 75% heap usage, and startup logs the heap limit. Raw documents are retained as compact JSON and parsed only for inspection; NDJSON loads normalize each line immediately and snapshot writes use bounded batches over shallow copies of document maps. Full-text caching stays within the measured memory budget; previous slots expire after 24 hours by default. Under WinSW, sustained high heap usage drains connections for up to five seconds, flushes loaded stores and exits 75 so the wrapper restarts it. A persisted one-hour cooldown prevents repeated recycling. Plain terminal runs do not automatically recycle; set MEMORY_RECYCLE_MB explicitly with another supervisor. Existing store files and protocol replies remain compatible.

Inspect the proposed install without admin, downloads, file writes or service/port changes:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 plan -RuntimeRoot "$env:TEMP\GraphServicePlan"
```

Upgrade from the repository: stop the service, pull and install, then start it again (`npm run service:restart` restarts it in one step if you prefer):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 stop
git pull
npm install
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 start
```

`npm run service:status` reports service state, PID, listening processes and `/health`. When `LdaGraph` is not installed but the old `OptimizelyGraphLocal` service is, status says so and points to [Upgrading from an older install](#upgrading-from-an-older-install-optimizelygraphlocal). `npm run service:logs` prints the last 50 lines of each current wrapper/stdout/stderr log. `npm run service:restart` restarts it. Start or stop manually with `powershell -ExecutionPolicy Bypass -File scripts\service.ps1 start` (or `stop`). Install/start/stop/restart/uninstall request UAC when needed.

Uninstall keeps runtime data and prints its location:

```powershell
npm run service:uninstall
```

To explicitly delete that runtime too, run `powershell -ExecutionPolicy Bypass -File scripts\service.ps1 uninstall -RemoveData`. This permanently removes credentials, stores and logs. Unsafe removal targets and runtimes containing junctions/symlinks are rejected.

If the port is occupied by another process, install/start fails with its PID/name; choose a free `-Port` on install. It never stops that process. If startup fails or health remains unavailable after 20 seconds, inspect `service:logs` and Windows Event Viewer. Check that Node, repository files and dependencies remain accessible to LocalService. Moving the repository requires reinstalling from its new location. A custom port changes the CMS GatewayAddress in Connect.

Service tests use temporary runtimes and ephemeral ports. On Windows they deliver SIGBREAK/SIGINT/SIGTERM process events via IPC because Node's `child.kill()` force-terminates a Windows child; POSIX SIGINT/SIGTERM use OS signals. They verify the production CLI flushes pending stores before exit. UAC, SCM installation and WinSW console-signal delivery require a separate elevated installation check.

## Upgrading from an older install (OptimizelyGraphLocal)

Installs made before the rename to LDA Local Graph run as the Windows service `OptimizelyGraphLocal`. The current script manages the service `LdaGraph` and does not see the old one.

**Recommended:** run `lda adopt` from the LDA CLI. It keeps your existing data folder and port and registers the service under the new id `LdaGraph`.

**Manual:** `powershell -ExecutionPolicy Bypass -File scripts\service.ps1 uninstall` cannot see the old service id, so stop and remove the old service yourself from an elevated (Run as administrator) prompt. This removes only the service registration; the data folder is not touched:

```powershell
sc.exe stop OptimizelyGraphLocal
sc.exe delete OptimizelyGraphLocal
```

Then install the new service on the old runtime folder (the folder that holds `tenants.json`, `data\`, `logs\` and `service\`):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\service.ps1 install -RuntimeRoot "<old runtime folder>" -MaxMemoryMB 16384
```

`-MaxMemoryMB` is optional; pass the heap size the old service used if it was not the default. Install does not read the old service's settings, so also pass `-Port <n>` if the old service did not use port 8082. Existing tenants, data and logs are kept. The old `OptimizelyGraphLocal.exe` and `OptimizelyGraphLocal.xml` files in `service\` are no longer used and can be deleted.

## Performance

Measured on Windows with Node 24.11.1, 60,000 synthetic documents, 20 types, two locales and mixed HTML. Times below are round-trip p95 milliseconds after three warmups, with 12 idle samples and 32 samples in four waves of eight clients. Both versions ran as separate children on ephemeral ports with in-memory data and logs; 1.0.2 used a read-only checkout.

| Query | 1.0.2 idle | 1.1.0 idle | 1.0.2 eight clients | 1.1.0 eight clients |
| --- | ---: | ---: | ---: | ---: |
| Key lookup | 247.3 | 1.3 | 2090.4 | 6.9 |
| URL lookup | 494.4 | 1.6 | 2688.5 | 4.6 |
| Typed list, 50 items | 53.1 | 10.3 | 350.3 | 57.3 |
| Facets | 203.4 | 202.4 | 1389.7 | 1254.1 |
| Full-text match | 831.8 | 84.2 | 5083.9 | 575.7 |
| CMS search with ranking | 809.4 | 88.9 | 5209.2 | 644.4 |

All specified targets were met. Full-text-only caching added 30.6 MiB of retained heap after forced GC (15.2% above the same indexed store without caches). All-field caching measured 60.3%, so field token caches and retained stripped texts were omitted. Dirty 60,000-document shutdown flushes took 436–516 ms; an already saved store skipped its snapshot. On Windows the signal benchmark dispatches SIGINT/SIGTERM/SIGBREAK process events through IPC, as the service tests do.

Run `node scripts/bench-query.mjs` for the default workload; pass `--root <read-only-checkout>` for another version, or `--docs`, `--samples`, `--rounds` and `--output` to adjust the run. Run `node --expose-gc scripts/bench-memory.mjs`, `node scripts/bench-shutdown.mjs` and `node scripts/check-query-compat.mjs <baseline-checkout>` for the memory, shutdown and result comparisons. The scripts write raw measurements to `perf-results/` (not committed). These are warm-query measurements; tenant loading and lazy index construction happen before timing.

Automatic recycling requires Windows plus both `BASE` and `SERVICE_ID`. [WinSW 2.12.0's XmlServiceConfig.cs, lines 51–60](https://github.com/winsw/winsw/blob/v2.12.0/src/WinSW.Core/Configuration/XmlServiceConfig.cs#L51-L60) sets these variables in the wrapper environment inherited by the child. After a recycle, three high readings immediately after startup or a tenant load disable recycling for that process and warn that the live data needs a higher heap or recycle limit. `_recycle.json` records `lastStartAboveThreshold`; later process starts reassess the limit. Invalid or negative `PREVIOUS_SLOT_HOURS` values warn and use the default 24 hours.

## Limitations

- Queries still run on one JavaScript thread. Type, ID, key and URL indexes narrow candidates; general predicates and aggregations still scan their candidates. The full-text-only cache avoids repeated tokenization; field searches retokenize to stay within the measured memory budget. Recycling pauses availability while the wrapper restarts; standalone positive thresholds also exit 75 and require a restart supervisor. `LOG_DIR=:memory:` cannot retain the cooldown across restarts.
- For public queries, documents belonging to a non-default content source with no `_metadata.status` are treated as Published. Everyone-read ACL, expiry and deletion checks still apply. This visibility rule is an approximation of the real service; Basic and preview behavior is unchanged.
- Click tracking cannot round-trip locally: the CMS only forwards HTTPS URLs on `*.cg.optimizely.com`. `_track` returns null. The optional `_link` field is omitted.
- Semantic ranking uses text relevance. Search has no language stemming or synonym expansion; fuzzy matching uses the local edit-distance rules above.
- This is an in-process local evaluator, without remote extraction, distributed indexing, or webhook delivery. `/extract` supports plain text, PDF and Word `.docx`; unsupported binary formats return empty text. Webhook registrations are stored. The `pinned` argument is accepted but has no configured collections to apply.
- Rebuilds swap the whole pending slot; mutation language arguments are accepted but do not partition promotion. Numeric factor/date decay scores are local approximations of the hosted scoring implementation.
- Schema rebuild failures are logged and preserve the last valid schema. Unknown model types become JSON, invalid names are sanitized, and duplicate sanitized names are skipped. Large request bodies have a 64 MB limit.
